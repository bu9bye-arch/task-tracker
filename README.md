# task-tracker

一个为 coding agent 维护长期任务事实、交接状态和高风险操作记录的轻量 skill。

> A lightweight skill that helps coding agents preserve durable task state, hand off work, record repeated attempts, and keep high-impact operations auditable.

## 它解决什么问题

长任务最容易丢失的往往不是代码，而是上下文：目标变过几次、哪些办法已经失败、用户授权了什么、还有哪些风险没有验证。对话一长、会话一换或多人并行后，这些事实如果只留在聊天里，就很容易被遗漏或误解。

`task-tracker` 让 agent 在真正需要时维护一张精简的任务卡，记录目标、验收标准、当前状态、关键决定、尝试结果、阻塞、验证证据和下一步。它也为发布、生产、数据和权限等高影响操作提供最小留痕要求。

它不是待办清单应用，也不要求每个小任务都创建文档。一次性答疑和确定性小改应该直接完成，只有需要跨会话交接、并行协作、反复尝试或风险审计时才启用。

## 这个 skill 的来历

我的 vibe coding 历程从 Gemini 2.5 Pro 开始。刚开始时，我没有编程基础，也没有亲手编辑代码的经验。我会做的事情，基本就是把目标、问题和不满意的地方告诉 AI，再观察结果是否真的解决了问题。

`task-tracker` 最初不是来自一套现成的工程方法，而是来自我自己的实际需求：任务一长，AI 会遗忘早先的决定；程序意外中断，或者需要切换会话、更换模型时，新会话也很难知道前面的工作进行到了哪里。

这些丢失的上下文往往正是最重要的部分：一个 Bug 已经尝试过哪些解决方向，用户对任务目标做过哪些修正，上一次操作停在哪一步，还有哪些结果没有验证。涉及发布或重要修改时，一句“完成了”也不能说明哪些结果已有证据、哪些仍待验证。于是我提出了最早的任务记录需求，并在一次次真实使用中让 AI 帮我调整它。

后来的迭代吸收了 [Superpowers](https://github.com/obra/superpowers) 给我的一些重要启发，例如先对齐再执行、用证据而不是口头声明完成、为复杂工作保留检查点，以及让不同阶段可以被可靠交接。这些理念没有被原样照搬，而是与我长期使用中遇到的问题结合，逐渐收敛成现在这个更专注于“持久任务状态”的 skill。

从 Gemini 2.5 Pro 到现在的 GPT-5.6，这个版本经历了大量实际任务的反复使用和修改。它也记录了一种对我很重要的创作方式：即使没有传统编程背景，人仍然可以提出问题、定义标准、判断结果，并通过长期迭代把 AI 生成的内容打磨成真正适合自己的工具。

## 适用场景

- 跨会话继续一个尚未完成的任务。
- 把工作交给另一位 agent、协作者或新会话。
- 多个方向并行推进，需要共享稳定事实。
- 排障经历了多次尝试，需要避免重复走弯路。
- 发布、生产、数据、权限或外部写入需要记录授权、验证和回退方式。

不建议用于一次性问答、无需交接的短任务，或只改一个确定位置的简单修改。

## 与 Superpowers 有什么不同

`task-tracker` 和 Superpowers 不是替代关系。Superpowers 是一套覆盖需求澄清、计划、实现、测试、调试和评审等环节的完整开发方法；`task-tracker` 则只解决一个更窄的问题：让任务的关键事实能够跨会话、跨模型和跨执行阶段保存下来。

| 对比维度 | `task-tracker` | Superpowers |
|---|---|---|
| 定位 | 单一、轻量的任务状态记录 skill | 由多个 skills 组成的完整开发工作流 |
| 主要问题 | 防止目标、决定、尝试、授权和验证状态随会话切换而丢失 | 规范从需求到实现、测试和收尾的执行过程 |
| 主要产物 | 任务卡、活跃任务索引和高影响操作记录 | 设计、计划、测试、评审及各阶段的执行结果 |
| 启用方式 | 只在长任务、交接、反复尝试或高风险操作中按需启用 | 在开发任务的不同阶段触发对应 skill |
| 过程约束 | 只规定需要记录哪些事实，不限定具体的开发或测试方法 | 为设计、实现、测试和评审等阶段提供具体工作流与检查要求 |

两者可以一起使用：Superpowers 负责指导任务应该怎样推进，`task-tracker` 负责保存推进过程中不能丢失的状态。只需要轻量交接和持续记录时，也可以单独使用 `task-tracker`。

## 安装

克隆仓库：

```bash
git clone https://github.com/bu9bye-arch/task-tracker.git
cd task-tracker
```

安装到 Codex 的个人 skills 目录：

```bash
mkdir -p ~/.agents/skills
cp -R task-tracker ~/.agents/skills/
```

如果你的环境配置了不同的个人 skills 目录，请以该环境显示的发现路径为准，不需要重复安装。安装后重启 Codex 或新建任务，让 skill 列表重新加载。

## 使用

当请求涉及持续台账、交接、并行推进、多次尝试或高影响操作时，Codex 可以根据描述自动触发它。也可以明确指定：

```text
使用 $task-tracker 记录这个发布任务，保留授权范围、验证结果和回退方式。
```

`task-tracker` 会先读取项目已有的任务约定；没有约定时才提出最小目录和稳定编号。任务卡只记录后续接手真正需要的事实，不应写入密钥、Token、完整环境变量或未经脱敏的个人数据。

## 设计原则

- 按需启用：不为短任务制造文档负担。
- 事实优先：区分已确认、待验证和阻塞，不把猜测写成结论。
- 便于交接：下一位接手者能知道当前状态、证据和下一步。
- 高风险留痕：记录授权范围、影响面、验证门槛与回退方式。
- 最小记录：长日志和完整 diff 留在合适的产物中，任务卡只保留摘要和链接。

## 隐私与安全

公开前已对当前版本进行人工和模式扫描，未发现个人联系方式、凭据、私钥、内部地址或可执行的危险脚本。`task-tracker` 本身也明确禁止把密钥、Token、完整环境变量和未脱敏个人数据写进任务记录。

这仍然是一组交给 AI agent 执行的工作指引，不是权限隔离或备份系统。涉及生产、发布、数据和不可逆操作时，仍应使用平台自身的权限控制、审核与回退机制。
